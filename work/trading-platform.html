Custodial wallet & trading platform

  • NestJS
  • Next.js
  • TypeScript
  • Postgres
  • TypeORM
  • WebSockets
  • M-Pesa Daraja
  • Docker

Built for a client in 2026. The code is private, so this page describes the design instead. It is pre-launch: real-money payments are built but switched off until licensing is settled.

The problem

Customers hold a wallet on the platform, top it up from their phone, and trade short contracts on live synthetic indices, by hand or through an automated bot. The platform is the counterparty on every trade. That makes it a money system before it is a trading app: every shilling has to be accounted for, under retries, timeouts and two admins clicking at once.

What I built

  • One ledger, one door for money. Deposits, trade stakes, payouts and adjustments all go through the same ledger service. A debit locks the wallet row, re-checks the balance and appends the entry in a single transaction, which closed a check-then-debit race in an earlier version.
  • M-Pesa deposits and withdrawals. STK Push and status queries behind a payment-gateway interface, with a fake gateway for development and CI. Settlement matches the provider's reference under a lock and is idempotent, so a repeated callback can't credit twice. A withdrawal that fails downstream is reversed with its own ledger entry.
  • Currency quotes that can't drift. The customer sees a live KES to USD quote as they type. The server re-quotes on submit and records the exact rate and credited amount on the payment.
  • Reconciliation. Every 15 minutes a job compares ledger totals with the live balance and flags any drift. Admins can also run it on demand.
  • Maker-checker approvals. Withdrawal approvals and balance adjustments don't apply when the first admin clicks. They file a request that takes effect only when a different admin approves it.
  • Risk controls. A kill switch plus per-customer, per-symbol and platform-wide exposure caps, checked inside the same locked transaction that accepts a trade. The bot checks the kill switch on every tick and stops after repeated rejections instead of retrying forever.
  • Live prices. 13 instruments, one upstream WebSocket subscription per symbol, fanned out to every connected browser. The line and candlestick charts are hand-written SVG: history is backfilled over REST and the current candle updates from the same tick stream. No charting library.
  • KYC. Document upload to local disk or S3-compatible storage, retention rules, and an audit-log entry every time an admin opens a document.

A detail I'm glad I caught

Access tokens last 15 minutes and several screens poll, so many tabs hit an expired token at the same moment. Refresh tokens are single-use by design, so two parallel refreshes would burn each other and log the customer out. The fix was to make the client's refresh single-flight: one refresh, and every waiting request replays with the new token. A test keeps that behaviour in place.

How it was built

  • NestJS API with one module per responsibility (auth, trading, payments, fx, risk, bot, kyc, admin) and a Next.js App Router front end.
  • Jest unit and end-to-end tests on the API, Vitest on the web app, all in CI.
  • An architecture document that records what is actually true today, including the parts that are easy to assume otherwise.
